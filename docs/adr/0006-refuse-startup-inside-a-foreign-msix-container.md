# Refuse startup inside a foreign MSIX container

When Skilly is launched from a process tree hosted by an MSIX-packaged application (for example a terminal spawned by the packaged Claude desktop app), Windows filesystem virtualization silently redirects every write under `%LOCALAPPDATA%` into that package's private `LocalCache`. The authority state then forks: Management Records written inside the container are invisible to normally launched instances, while Skill content under the user profile root lands for real — installations look Unmanaged even though they were installed through Skilly. `App.OnStartup` therefore refuses to start with an explanatory dialog when it detects the redirection. Detection writes a throwaway probe file into the application root and looks for it under `Packages\*\LocalCache\Local\Skilly` (`Infrastructure/MsixVirtualization.cs`); the obvious alternative, `GetCurrentPackageFullName`, was rejected because processes that merely inherit the container's filesystem silo carry no package identity and the API reports no package. A read-only mode was also rejected because reads are equally virtualized: the window would display the container's shadow state as if it were authoritative.
