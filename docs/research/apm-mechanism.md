# How APM installs and maintains agent skills

Research date: 2026-08-26

## Scope and inspected versions

This note answers the research question only. It records observable behavior and limitations; it does not select a Source Provider contract, installation topology, or product policy for Skilly.

The relevant released tool is **Microsoft APM (Agent Package Manager)** from [`microsoft/apm`](https://github.com/microsoft/apm). The behavior below is pinned to release **v0.28.0**, source commit [`e041462f4a48086dbee3da145c07d71b8a3b84fd`](https://github.com/microsoft/apm/tree/e041462f4a48086dbee3da145c07d71b8a3b84fd), published 2026-08-06. The repository declares Python package `apm-cli` version `0.28.0` and console entry point `apm`; PyPI has matching version-specific `0.28.0` wheel and source records, while the GitHub release includes a Windows x86-64 ZIP and SHA-256 sidecar ([package metadata](https://github.com/microsoft/apm/blob/v0.28.0/pyproject.toml#L5-L13), [entry point](https://github.com/microsoft/apm/blob/v0.28.0/pyproject.toml#L62-L64), [PyPI JSON](https://pypi.org/pypi/apm-cli/0.28.0/json), [release](https://github.com/microsoft/apm/releases/tag/v0.28.0)).

### Identification and ambiguity

`microsoft/apm` is the strongest match because its own released README expands APM as "Agent Package Manager," describes skills as installable dependencies, and explicitly names GitHub Copilot, Claude Code, OpenCode, and Codex as targets ([README](https://github.com/microsoft/apm/blob/v0.28.0/README.md#apm--agent-package-manager), [skill example](https://github.com/microsoft/apm/blob/v0.28.0/README.md#why-apm)). This also matches the ticket's requested operations: the released CLI has `install`, `outdated`, `update`, and `uninstall` commands for agent packages and skill subsets ([install](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/install.md), [outdated](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/outdated.md), [update](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/update.md), [uninstall](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/uninstall.md)).

The acronym is not globally unique, so this identification is strong rather than logically certain:

- [`githubnext/apm`](https://github.com/githubnext/apm) also calls itself Agent Package Manager. Its inspected unversioned `main` commit [`b3db26d008d0a12a499a70fd03dd18d0f81534f2`](https://github.com/githubnext/apm/tree/b3db26d008d0a12a499a70fd03dd18d0f81534f2) says it is an **experimental Go migration**, retains the Python CLI as the reference/parity oracle, and documents local build/parity commands rather than a separate user-facing package identity. It therefore appears to be an experimental implementation track for the same APM behavior, not the released provider independently implied by the ticket ([README](https://github.com/githubnext/apm/blob/b3db26d008d0a12a499a70fd03dd18d0f81534f2/README.md)).
- [`withastro/rosie`](https://github.com/withastro/rosie) describes itself generically as an "Agent package manager" and package `rosie-skills` v0.8.5 as a package manager for AI agent skills, but its product and executable are named **Rosie**, not APM ([v0.8.5 README](https://github.com/withastro/rosie/blob/v0.8.5/README.md), [v0.8.5 release](https://github.com/withastro/rosie/releases/tag/v0.8.5)). It is a competing first-party skill manager, not the most plausible expansion of the capitalized provider name "APM."

## Windows CLI and package addressing

### Installing and invoking the CLI

The official Windows bootstrap is PowerShell `irm https://aka.ms/apm-windows | iex`. In v0.28.0 the installer selects `apm-windows-x86_64.zip`, verifies the published sidecar when available, and defaults to `%LOCALAPPDATA%\Programs\apm`: versioned bundles go under `releases\<tag>`, `current` is a junction to the selected release, and `bin\apm.cmd` is a compatibility shim. Both `current` and `bin` are added to the user `PATH`, with `current\apm.exe` first, so native process APIs can launch bare `apm`; `APM_INSTALL_DIR` changes the bin/shim location and sibling install root ([installation docs](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/getting-started/installation.md#quick-install-recommended), [Windows PATH contract](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/getting-started/installation.md#L30-L33), [installer paths](https://github.com/microsoft/apm/blob/v0.28.0/install.ps1#L82-L102), [promotion and junction](https://github.com/microsoft/apm/blob/v0.28.0/install.ps1#L797-L951), [shim and PATH](https://github.com/microsoft/apm/blob/v0.28.0/install.ps1#L953-L1013)). Windows ARM64 currently receives the x86-64 binary and depends on emulation; Scoop and `pip install apm-cli` are documented alternatives ([requirements and ARM64 caveat](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/getting-started/installation.md#requirements), [Scoop and pip](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/getting-started/installation.md#package-managers)).

This CLI installation location is separate from APM package state and separate again from harness-visible skill copies.

### Addressing a skill or collection

`apm install [PACKAGE_REF...]` accepts GitHub `owner/repo`, an optional `#tag`, `#branch`, full commit, or semver constraint, full HTTPS/SSH Git URLs, host-qualified shorthand, a repository subdirectory such as `owner/repo/skills/review`, a single primitive file, marketplace `name@marketplace[#ref]`, packed bundles, and local paths ([reference forms](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/consumer/manage-dependencies.md#reference-formats), [install argument](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/install.md#description)). The parser explicitly recognizes Windows drive paths (`C:\...` and `C:/...`) plus `./`, `.\`, `../`, `..\`, `/`, `~/`, and `~\` as local paths ([source](https://github.com/microsoft/apm/blob/v0.28.0/src/apm_cli/models/dependency/reference.py#L302-L323)).

Repository layout determines skill identity and deployment. A root `SKILL.md` is one skill bundle copied as a unit; `skills/<name>/SKILL.md` is a collection whose children are promoted independently; `.apm/skills/<name>/SKILL.md` supplies package primitives; and plugin manifests can expose declared skills ([package layouts](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/package-types.md#layout-summary)). For a collection or plugin, repeatable `--skill NAME` selects skills and persists the subset in both `apm.yml` and `apm.lock.yaml`; separate installs union selections, `--skill '*'` resets to all, and removing one selection requires editing `apm.yml` before reinstalling ([selective install](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/package-types.md#skill-collection-skillsnameskillmd), [exact CLI outcomes](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/install.md#skill-subset)).

## Install locations and four-harness exposure

APM has project and user scopes:

| Layer | Project scope | User/global scope | Evidence |
| --- | --- | --- | --- |
| Manifest | `./apm.yml` | `~/.apm/apm.yml` | [`install -g`](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/install.md#target-selection), [`deps` scope](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/deps.md#description) |
| Resolved source cache | `./apm_modules/` | `~/.apm/apm_modules/` | [`deps` scope](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/deps.md#description) |
| Provenance/ownership state | `./apm.lock.yaml` | `~/.apm/apm.lock.yaml` | [lockfile location](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/lockfile-spec.md#location), [`deps why -g`](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/deps.md#apm-deps-why) |
| Harness-visible skills | selected target directories | selected target directories below the user's home | [targets matrix](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/targets-matrix.md), [global install](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/install.md#target-selection) |

`--target` accepts a comma-separated explicit target list and has precedence over manifest `targets:`, saved target configuration, and filesystem auto-detection. With no selected/detected target, install exits `2`; explicit targets are therefore the documented way to avoid machine-dependent detection ([target option and precedence](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/install.md#target-selection), [detection rules](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/targets-matrix.md#detection-and-resolution)).

For the ticket's four harnesses, v0.28.0 supports skills as follows:

| Target slug | Project skill path | User-scope interpretation | Relevant limitation/effect |
| --- | --- | --- | --- |
| `copilot` | `.agents/skills/<name>/SKILL.md` | Under the user home, the converged path is `~/.agents/skills/<name>/SKILL.md` | Copilot's other user primitives use `~/.copilot`, but skills use the converged `.agents` root. |
| `opencode` | `.agents/skills/<name>/SKILL.md` | `~/.agents/skills/<name>/SKILL.md` | OpenCode's native user root is `~/.config/opencode`, but skills use the converged `.agents` root. |
| `codex` | `.agents/skills/<name>/SKILL.md` | `~/.agents/skills/<name>/SKILL.md` | Codex's other files use `.codex`; skills use `.agents`. |
| `claude` | `.claude/skills/<name>/SKILL.md` | `~/.claude/skills/<name>/SKILL.md`, honoring `CLAUDE_CONFIG_DIR` for the Claude root | Claude remains on its target-native skill directory rather than the converged path. |

These paths and the convergence exception are stated in the canonical target matrix ([summary and convergence](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/targets-matrix.md#summary), [Copilot](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/targets-matrix.md#copilot), [OpenCode](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/targets-matrix.md#opencode), [Codex](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/targets-matrix.md#codex), [Claude](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/targets-matrix.md#claude), [skills convergence](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/targets-matrix.md#skills-convergence)). Thus an explicit global install can address all four with `apm install -g PACKAGE --target copilot,opencode,codex,claude`; the first three converge on one destination and Claude receives a second copy. The implementation de-duplicates identical resolved destination roots but uses `shutil.copytree` for each distinct destination; it does not create cross-harness links or junctions ([copy and de-dup implementation](https://github.com/microsoft/apm/blob/v0.28.0/src/apm_cli/integration/skill_integrator.py#L1035-L1154)). `--legacy-skill-paths` (or `APM_LEGACY_SKILL_PATHS=1`) opts back into per-client skill directories ([convergence switch](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/targets-matrix.md#skills-convergence)).

## Provenance and persisted state

`apm install PACKAGE` adds the direct declaration to `apm.yml`; a bare install resolves that manifest, downloads the full transitive graph to `apm_modules`, scans it, deploys target files, and writes `apm.lock.yaml` ([install pipeline](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/consumer/install-packages.md#what-apm-install-does)). `apm_modules` is rebuildable cache rather than the durable record; project guidance says to ignore it while committing `apm.yml`, `apm.lock.yaml`, and deployed target files ([commit guidance](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/consumer/install-packages.md#what-to-commit)).

The lockfile is the principal provenance and ownership record. Per dependency it can store canonical `repo_url`, host, requested `resolved_ref`, exact Git `resolved_commit`, registry `resolved_url` and `resolved_hash`, package/skill type, virtual subpath, dependency depth and parent (`resolved_by`), selected skills and targets, marketplace discovery/source metadata, source and deployed content hashes, and every `deployed_file`; top-level canonical deployment rows record target, scope, all owners, active owner, locator, and content hash ([lockfile purpose](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/lockfile-spec.md#purpose), [deployment rows](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/lockfile-spec.md#canonical-deployment-rows), [per-entry fields](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/lockfile-spec.md#per-entry-fields)). A Git/local package's manifest `name`, `version`, description, and license are author claims rather than trust anchors; the lockfile specification explicitly says identity/provenance must use repository plus resolved commit, or a registry hash ([field trust boundary](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/lockfile-spec.md#L184-L225)).

The harness copy itself does not receive an APM provenance sidecar or injected metadata. Skill trees are copied from `apm_modules` and Markdown links may be rewritten; ownership remains centralized in the scope's lockfile ([copy implementation](https://github.com/microsoft/apm/blob/v0.28.0/src/apm_cli/integration/skill_integrator.py#L975-L999), [copy operation](https://github.com/microsoft/apm/blob/v0.28.0/src/apm_cli/integration/skill_integrator.py#L1139-L1154)). Consequently, a skill found only in a harness directory is not self-describing as APM-managed; association requires the corresponding `apm.lock.yaml` deployment rows.

## Checking and applying updates

APM separates checking, package updates, and CLI updates:

- `apm outdated` is read-only. It reads the selected scope's lockfile and queries authenticated upstreams: tags use semver comparison, branches compare locked SHA to remote tip, absent refs compare the default branch, full-SHA pins compare to the latest annotated semver tag, and marketplace/experimental registry sources use their own current-version rules. Local and Artifactory dependencies are skipped; an unreachable/unresolvable authoritative source is reported as `unknown`, not `up-to-date` ([comparison rules](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/outdated.md#description), [status values](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/outdated.md#status-values)). `-g` checks `~/.apm`; exit is `0` after a completed check even when updates exist and `1` only when no lockfile exists, so exit status cannot signal "updates available" ([options and exit codes](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/outdated.md#options), [exit codes](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/outdated.md#exit-codes)).
- `apm update` re-resolves all or named dependencies against the latest allowed upstream refs, renders added/updated/removed/unchanged sections, and prompts once with default **No** before writes. `--yes` is required to apply in a non-interactive process; `--dry-run` computes the plan without writing; `-g` applies to user scope. A failure to resolve a mutable ref from authoritative upstream fails rather than accepting a stale cached ref ([workflow](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/update.md#description), [options](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/update.md#options), [freshness behavior](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/update.md#behavior)). `apm install --update` is the non-prompting install-path alternative that re-resolves and rewrites the lockfile; normal and frozen installs otherwise replay locked commits ([install update/frozen flags](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/install.md#common), [lock replay](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/install.md#behavior)).
- Reinstall/update removes files a still-present package no longer deploys only when their recorded hashes still match; edited files remain with a warning. The lockfile's hashes and deployment ledger also support explicit drift checks through `apm audit` ([stale-file cleanup](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/install.md#behavior), [audit modes](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/audit.md#description)).
- `apm self-update --check` checks the CLI release without applying it; `apm self-update` downloads and runs the platform installer. Package updates are intentionally separate. APM also performs a cached, non-blocking CLI release check at most daily during normal commands ([self-update behavior](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/self-update.md#behavior), [startup notification](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/self-update.md#startup-update-notification)).

## Removal behavior

`apm uninstall [-g] PACKAGES...` accepts shorthand, URL, host-qualified, marketplace, exact local path, or the `_local/<name>` key reported by `apm deps list`; revision fragments do not participate in uninstall identity ([arguments](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/uninstall.md#arguments), [revision behavior](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/uninstall.md#ref-is-not-meaningful-for-uninstall)). It removes the direct manifest entry, source cache directory, now-unneeded transitive dependencies, lockfile-tracked deployed files and hook/MCP contributions, lock entries, and empty directories. If no dependency state remains, the lockfile is deleted; hand-authored files outside lock ownership are not selected ([ordered behavior](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/uninstall.md#behavior), [tracked-file boundary](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/uninstall.md#description)).

Selection is atomic: if any requested name is absent or ambiguous, no package in that invocation is selected and no lifecycle script or APM filesystem write occurs. The operation as a whole is not documented as transactional after selection; source shows manifest writes precede package/deployment/MCP cleanup and emits recovery instructions for partial cleanup failures ([selection guarantee](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/uninstall.md#behavior), [write and cleanup sequence](https://github.com/microsoft/apm/blob/v0.28.0/src/apm_cli/commands/uninstall/cli.py#L211-L438)). `--dry-run` previews the uninstall engine but is not side-effect-free because trusted `pre-uninstall` lifecycle scripts still run ([dry-run caveat](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/uninstall.md#no-lockfile-behavior)).

## Authentication and credential handling

Public GitHub packages require no authentication. For private GitHub/GHE, APM checks explicit environment tokens and then automatically calls `gh auth token --hostname <host>`; a pre-authenticated `gh` session therefore works without APM storing another GitHub credential. SSH dependencies use already-loaded SSH keys, and generic Git hosts can use the existing Git credential helper ([authentication summary](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/consumer/authentication.md#the-30-second-answer), [`gh` integration](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/consumer/authentication.md#already-signed-in-with-gh), [SSH](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/consumer/authentication.md#ssh-clone-prerequisites), [generic Git credentials](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/consumer/authentication.md#bitbucket-gitea-and-any-other-git-host)).

Provider-specific environment variables include `GITHUB_APM_PAT`, `GITLAB_APM_PAT`, and `ADO_APM_PAT`; Azure DevOps Services may instead use an active Azure CLI session, while Azure DevOps Server is PAT-only. Experimental registries can take `APM_REGISTRY_TOKEN_<NAME>` or a token in `~/.apm/config.json`; the latter is machine-local persisted state and therefore differs from the Git/`gh` credential reuse path ([provider flows](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/consumer/authentication.md), [registry token configuration](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/install.md#install-from-a-private-registry-experimental)).

## Machine-readable output and exit behavior

There is no uniform machine-readable lifecycle API in v0.28.0:

| Need | Available contract | Limitation | Evidence |
| --- | --- | --- | --- |
| Resolved package/provenance inventory | Parse `apm.lock.yaml`; it is the pinned dependency and deployment record. | Working-draft lockfile versions `"1"` and `"2"` coexist; fields are not a single finalized schema. | [lockfile spec](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/lockfile-spec.md#purpose) |
| Installed dependency list/tree | `apm deps list`, `tree`, and `info` | Human tables/text; no `--json` for list/tree/info. `apm list` is scripts, not packages. | [`deps` options](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/deps.md), [`apm list` distinction](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/list.md#description) |
| Why a dependency is installed | `apm deps why PACKAGE --json` writes one JSON document to stdout and diagnostics to stderr. | This is a reverse-dependency query, not a complete inventory. Exit `0` success, `1` missing/ambiguous package, `2` missing lockfile. | [`deps why`](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/deps.md#apm-deps-why) |
| Resolved harnesses | `apm targets --json [--all]` returns target/status/source/deploy directory/needs rows. | Reports target resolution, not installed skills. Exit is always `0` when output is printed, including all-inactive. | [`targets --json`](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/targets.md#options), [exit](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/targets.md#exit-codes) |
| Integrity/drift | `apm audit --ci --format json` or `apm audit -f json`; JSON includes a `passed` boolean. | Audit answers integrity/policy, not update availability. CI exit `0` pass, `1` failure; non-CI additionally uses `2` for warnings/usage and `3` for infrastructure/configuration. | [audit output](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/audit.md#output), [audit exits](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/audit.md#exit-codes) |
| Update availability | `apm outdated` prints a human table. | No JSON option, and both up-to-date and outdated results exit `0`; `unknown` rows may represent per-source query failures. | [`outdated` options/status/exit](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/outdated.md#status-values) |
| Install/update/uninstall plan or result | Human-readable `--dry-run`/plan and diagnostics. | Their documented/implemented option sets have no JSON flag. Install explicitly uses `0` success, `1` operational failure, `2` usage/target-selection failure; update/uninstall use `1` for operational failures and Click uses `2` for malformed CLI usage. | [install options and exits](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/install.md#exit-codes), [update options](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/update.md#options), [uninstall options](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/uninstall.md#options), [update command source](https://github.com/microsoft/apm/blob/v0.28.0/src/apm_cli/commands/update.py#L371-L453), [uninstall command source](https://github.com/microsoft/apm/blob/v0.28.0/src/apm_cli/commands/uninstall/cli.py#L42-L61) |

Install's success code means all requested deployment completed, and any reported install error remains exit `1` even with `--force`; lack of a target and flag conflicts are exit `2` ([install exit table](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/install.md#exit-codes)). Update refusal has two different successful/no-write paths: an interactive **No** returns normally, while a non-interactive invocation that needs consent but lacks `--yes` exits `1` ([update consent implementation](https://github.com/microsoft/apm/blob/v0.28.0/src/apm_cli/commands/update.py#L655-L675)).

## Unresolved caveats

- The Skilly issue names only "APM" and provides no publisher/package identifier. The Microsoft tool is the evidence-backed match, but the ticket text alone cannot rule out a future rename, transfer, or intended use of another agent package manager.
- `githubnext/apm` is a first-party-looking competing repository with the same expanded name and a Go implementation, but the inspected README describes Microsoft APM's Python CLI as its reference oracle and does not explain the repositories' future release/ownership relationship ([inspected README](https://github.com/githubnext/apm/blob/b3db26d008d0a12a499a70fd03dd18d0f81534f2/README.md)).
- The published PyPI metadata summary still says "MCP configuration tool" even though the same v0.28.0 package README and source implement the broader Agent Package Manager behavior; the summary alone does not uniquely describe the package's functionality ([PyPI JSON](https://pypi.org/pypi/apm-cli/0.28.0/json), [released README](https://github.com/microsoft/apm/blob/v0.28.0/README.md)).
- APM v0.28.0 is project/package-oriented even at `--global` scope: installation creates a user manifest, cache, and lockfile and then copies skills into selected harness directories. It does not expose a single JSON command that combines installed skill identity, provenance, update status, and every harness copy ([global scope](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/deps.md#description), [machine-readable command boundaries](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/guides/operating-installed-context.md#at-a-glance)).
- The lockfile page labels the emitted v0.2 format a working draft and documents two active lockfile versions. Any external parser must account for that versioned state; this research does not decide whether Skilly should parse it or invoke APM commands ([lockfile purpose](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/lockfile-spec.md#purpose)).
- Update checking can produce human-only `unknown` rows while still exiting `0`, and install/update/uninstall have no JSON result mode. This research establishes the boundary but does not decide how another application should interpret or compensate for it ([outdated status and exit](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/outdated.md#status-values), [install options](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/install.md#options), [update options](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/update.md#options), [uninstall options](https://github.com/microsoft/apm/blob/v0.28.0/docs/src/content/docs/reference/cli/uninstall.md#options)).
