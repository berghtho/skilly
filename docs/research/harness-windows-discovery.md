# Global skill discovery on Windows

Research snapshot: 2026-08-26. Scope: local OpenCode, OpenAI Codex, Anthropic Claude Code, and GitHub Copilot clients on Windows. This is a source report, not an installation-topology decision.

## Answer in brief

There is no single user-level directory that all four harnesses officially discover. `~/.agents/skills` is the closest shared location: OpenCode, Codex, and GitHub Copilot document it as a personal/global skill root, while Claude Code documents only `~/.claude/skills` for personal skills. Therefore, one physical skill under `~/.agents/skills/<name>` needs a second exposure at `~/.claude/skills/<name>` for all four harnesses to see it. Codex and Claude Code explicitly support a symlinked skill directory; OpenCode's implementation follows symlinks; and the VS Code Copilot implementation explicitly handles the duplicate produced when `~/.claude/skills` points at `~/.agents/skills`. No reviewed vendor source promises that a Windows directory junction is treated identically to a symbolic link, and GitHub's Copilot CLI documentation does not promise symlink traversal, so a copy is the only fully documented filesystem-neutral fallback. [OpenCode docs](https://github.com/anomalyco/opencode/blob/13c27598d35f6f91fa4763a0b61a220ab7fcb263/packages/web/src/content/docs/skills.mdx) [Codex docs](https://developers.openai.com/codex/build-skills#where-codex-loads-local-skills) [Claude Code docs](https://code.claude.com/docs/en/skills#where-skills-live) [GitHub Copilot docs](https://github.com/github/docs/blob/be8d08aa6e3a95d7f531c6a00cbeff883e4e9814/content/copilot/concepts/agents/about-agent-skills.md)

## Evidence labels

- **Documented** means a current first-party product document or the Agent Skills specification says it.
- **Source observation** means current first-party implementation or tests show it, but the product documentation does not promise it.
- **Unknown** means the reviewed first-party material does not establish the behavior. Unknown behavior should not be inferred from another harness or from POSIX behavior.

In the tables below, `~` means the home directory of the environment in which the harness runs. For a native Windows process this is normally the Windows profile, so the user roots below are normally under `C:\Users\<user>`. Claude Code states this mapping explicitly as `%USERPROFILE%\.claude`, and Copilot CLI gives `C:\Users\YOUR-USER\.copilot` as its Windows example. A WSL process instead runs in Linux and uses its Linux home. [Claude settings](https://code.claude.com/docs/en/settings#find-or-create-your-settings-files) [Copilot CLI configuration](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference#file-location) [Codex WSL](https://developers.openai.com/codex/windows/wsl)

## Is `~/.agents/skills` shared?

| Root | OpenCode | Codex | Claude Code | GitHub Copilot |
| --- | --- | --- | --- | --- |
| `~/.agents/skills` | Yes | Yes | **No documented discovery** | Yes |
| `~/.claude/skills` | Yes | No | Yes | Common/CLI docs: no; VS Code: yes |
| `~/.copilot/skills` | No | No | No | Yes |
| `~/.config/opencode/skills` | Yes | No | No | No |

The `~/.agents/skills` row is directly stated in the OpenCode, Codex, and GitHub Copilot product documentation. Claude Code says that it follows the Agent Skills format, but format compatibility does not imply discovery from the standard-looking `.agents` path: its location table names only `~/.claude/skills` for personal skills, and a search of the first-party `anthropics/claude-code` repository at commit `005c5dade90c2c59c88d819d8723e7b579addb5e` found no `.agents/skills` reference. The absence is evidence of an **unknown/unsupported discovery path**, not proof that every build must reject it. ## One physical installation: exposure facts

These are consequences of the discovery tables, not a recommendation about which location Skilly should own:

| `~/.agents/skills/<name>` | OpenCode, Codex, GitHub Copilot | Add `~/.claude/skills/<name>` as a supported skill directory, a supported symbolic link where established below, or a copy. |

| `~/.config/opencode/skills/<name>` | OpenCode | Add both `~/.agents/skills/<name>` and `~/.claude/skills/<name>`, unless one is an exposure of the other. |

## Links, junctions, and copies

| Harness | Established behavior |
| --- | --- |
| OpenCode | The user docs do not promise links. **Source observation:** discovery invokes its glob scanner with `symlink: true`, so the current implementation follows filesystem symbolic links while finding `SKILL.md`. [OpenCode source](https://github.com/anomalyco/opencode/blob/13c27598d35f6f91fa4763a0b61a220ab7fcb263/packages/opencode/src/skill/index.ts#L140-L157) |
| Codex | **Documented:** "Codex supports symlinked skill folders and follows the symlink target." [Codex docs](https://developers.openai.com/codex/build-skills#where-codex-loads-local-skills) |
| Claude Code | **Documented:** an entry under an enterprise, personal, or project skills root may be a symlink to a directory; Claude follows it, and loads a target reachable from multiple locations only once. [Claude Code docs](https://code.claude.com/docs/en/skills#where-skills-live) |
| GitHub Copilot | GitHub's common and Copilot CLI skill docs do not promise symbolic-link or junction traversal. **VS Code source observation:** its duplicate logic explicitly names the case where `~/.claude/skills` is a symlink to `~/.agents/skills`, and deduplicates by canonical skill name. This establishes intended handling in that implementation, not a promise for every Copilot surface. [VS Code duplicate handling](https://github.com/microsoft/vscode/blob/4e4877b113b1c34f3f01f08138038fe564e84171/src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts#L529-L575) [GitHub CLI docs](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-skills) |

No reviewed first-party skill document or implementation test names an NTFS **directory junction** as supported. A junction may be traversed by ordinary filesystem APIs, but that equivalence is **unknown** for the four harness contracts and was not assumed here. A real directory copy is discoverable because each harness documents ordinary skill directories; unlike a link, however, a copy is a second mutable installation rather than another path to the same files. The sources establish discovery of the copy, not any synchronization behavior. [Agent Skills directory structure](https://github.com/agentskills/agentskills/blob/69ef37e9424c0a7ea9dd2293b559e43ec8176379/docs/specification.mdx#directory-structure)

### Duplicate side effect of cross-exposure

Exposing the same skill through both `~/.agents/skills` and `~/.claude/skills` makes both paths visible to OpenCode and to Copilot in VS Code:

- **OpenCode source observation:** it logs duplicate names and assigns the later parsed item into a name-keyed map. Parsing is launched with unbounded concurrency, so the implementation does not provide a reliable path precedence for duplicate names. The documentation instead tells users to keep names unique. [duplicate assignment](https://github.com/anomalyco/opencode/blob/13c27598d35f6f91fa4763a0b61a220ab7fcb263/packages/opencode/src/skill/index.ts#L112-L134) [concurrent loading](https://github.com/anomalyco/opencode/blob/13c27598d35f6f91fa4763a0b61a220ab7fcb263/packages/opencode/src/skill/index.ts#L235-L246) [uniqueness guidance](https://github.com/anomalyco/opencode/blob/13c27598d35f6f91fa4763a0b61a220ab7fcb263/packages/web/src/content/docs/skills.mdx#troubleshoot-loading)
- **VS Code source observation:** duplicate canonical names are sorted by scope priority and only the first is loaded. Workspace beats personal, then plugin, extension API, and extension contribution. The three default personal roots all have the same scope priority; the source does not define a separate contractual precedence among `.agents`, `.copilot`, and `.claude`. [priority function](https://github.com/microsoft/vscode/blob/4e4877b113b1c34f3f01f08138038fe564e84171/src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts#L1432-L1454) [default personal roots](https://github.com/microsoft/vscode/blob/4e4877b113b1c34f3f01f08138038fe564e84171/src/vs/workbench/contrib/chat/common/promptSyntax/config/promptFileLocations.ts#L169-L180)

## Metadata compatibility

The portable baseline is the Agent Skills directory format: one directory containing uppercase `SKILL.md`; YAML frontmatter with required `name` and `description`; `name` of 1-64 lowercase ASCII letters/digits separated by single hyphens, matching the parent directory; and a non-empty `description` of at most 1024 characters. `license`, `compatibility`, and string-to-string `metadata` are optional; `allowed-tools` is experimental in the standard and host support varies. **Specification fact.** [Agent Skills specification](https://github.com/agentskills/agentskills/blob/69ef37e9424c0a7ea9dd2293b559e43ec8176379/docs/specification.mdx#skillmd-format)

Material host differences:

- OpenCode recognizes `name`, `description`, `license`, `compatibility`, and `metadata`; its docs say unknown frontmatter is ignored. Thus standard `allowed-tools` has no documented OpenCode effect. [OpenCode metadata](https://github.com/anomalyco/opencode/blob/13c27598d35f6f91fa4763a0b61a220ab7fcb263/packages/web/src/content/docs/skills.mdx#write-frontmatter)
- Codex requires `name` and `description` in `SKILL.md`. Optional `agents/openai.yaml` controls OpenAI-specific presentation, invocation policy, and tool dependencies; it is not part of the cross-host `SKILL.md` baseline. [Codex metadata](https://developers.openai.com/codex/build-skills#optional-metadata)
- Claude Code local skills accept Claude-specific invocation, tool, model, context, hook, and path fields. Claude's docs explicitly separate those extensions from the six fields accepted by the Agent Skills packaging/upload path. For personal/project skills, the directory name remains the command name even when frontmatter `name` differs. [Claude frontmatter](https://code.claude.com/docs/en/skills#frontmatter-reference) [Claude command naming](https://code.claude.com/docs/en/skills#how-a-skill-gets-its-command-name)
- GitHub's common/CLI docs require `name` and `description`, permit `license`, and document `allowed-tools` for preapproval. VS Code additionally documents `argument-hint`, `user-invocable`, `disable-model-invocation`, and experimental `context`; it requires `name` to match the parent directory and silently rejects invalid names. [GitHub skill format](https://github.com/github/docs/blob/be8d08aa6e3a95d7f531c6a00cbeff883e4e9814/data/reusables/copilot/creating-adding-skills.md#L17-L78) [VS Code skill format](https://code.visualstudio.com/docs/agent-customization/agent-skills#_skillmd-file-format)

The common `name`/`description` subset and strict standard naming are therefore the only metadata assumptions established across all four. Optional host-specific fields may coexist, but their behavior is not portable merely because another host accepts them. [Agent Skills specification](https://github.com/agentskills/agentskills/blob/69ef37e9424c0a7ea9dd2293b559e43ec8176379/docs/specification.mdx#frontmatter)

## Material Windows constraints

1. **Native Windows and WSL have different homes.** OpenCode recommends WSL and stores its WSL state inside that environment; Codex says it runs inside Linux under WSL; Claude Code instructs users to install and launch the WSL build inside WSL; VS Code Remote runs extensions and file operations in WSL. Consequently a native `%USERPROFILE%\.agents\skills` tree is not the same discovery root as WSL `~/.agents/skills`. Cross-environment visibility requires a separately reachable WSL path and is outside the native-Windows path guarantees above. [OpenCode Windows](https://github.com/anomalyco/opencode/blob/13c27598d35f6f91fa4763a0b61a220ab7fcb263/packages/web/src/content/docs/windows-wsl.mdx) [Codex WSL](https://developers.openai.com/codex/windows/wsl) [Claude setup](https://code.claude.com/docs/en/setup#set-up-on-windows) [VS Code WSL](https://code.visualstudio.com/docs/remote/wsl)
2. **Use exact filename and portable casing.** The standard and product docs require `SKILL.md`; Windows' usual case-insensitive behavior can hide a casing error that later fails in WSL or another case-sensitive environment. The requirement, rather than Windows filesystem behavior, is the portable contract. [Agent Skills specification](https://github.com/agentskills/agentskills/blob/69ef37e9424c0a7ea9dd2293b559e43ec8176379/docs/specification.mdx#directory-structure) [GitHub Copilot requirement](https://github.com/github/docs/blob/be8d08aa6e3a95d7f531c6a00cbeff883e4e9814/data/reusables/copilot/creating-adding-skills.md#L15-L18)
3. **OpenCode's preferred Windows mode is WSL, not a different native skill root.** OpenCode says native Windows works but recommends WSL for filesystem performance and tool compatibility. Its skill documentation still defines roots relative to the running process's home. [OpenCode Windows](https://github.com/anomalyco/opencode/blob/13c27598d35f6f91fa4763a0b61a220ab7fcb263/packages/web/src/content/docs/windows-wsl.mdx) [OpenCode skills](https://github.com/anomalyco/opencode/blob/13c27598d35f6f91fa4763a0b61a220ab7fcb263/packages/web/src/content/docs/skills.mdx)
4. **Codex has native sandbox read boundaries, but discovery and execution are distinct.** Codex documents native Windows support and a command to grant sandbox read access to an absolute directory. A discovered skill whose scripts/resources resolve outside allowed roots may therefore encounter sandbox access controls even though its `SKILL.md` was found. [Codex Windows sandbox](https://developers.openai.com/codex/windows/windows-sandbox#grant-sandbox-read-access)
5. **Claude Code supports native Windows but not sandboxing there.** The supported native shell may be PowerShell/CMD, or Git Bash when installed; skill scripts that assume POSIX tooling are not made portable merely by successful discovery. [Claude Windows setup](https://code.claude.com/docs/en/setup#set-up-on-windows) [Claude skill `shell` field](https://code.claude.com/docs/en/skills#frontmatter-reference)
6. **Copilot CLI can relocate only its own configuration root.** `COPILOT_HOME` replaces `~/.copilot`, so it relocates the Copilot-owned `skills` directory; the docs do not say it relocates the independent `~/.agents/skills` compatibility root. [Copilot CLI configuration](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference#changing-the-location-of-the-configuration-directory)

## Unresolved caveats

- No reviewed first-party source establishes NTFS directory-junction support, junction deduplication, or the Windows privileges/policies required to create symbolic links for all four harnesses.
- Copilot's first-party surfaces are not perfectly uniform: GitHub's common and CLI docs list personal `.copilot` and `.agents`, while VS Code also lists personal `.claude`. The Copilot CLI implementation is not published in `github/copilot-cli`, so its link traversal and same-tier personal-root ordering could not be verified from source. [Copilot CLI repository](https://github.com/github/copilot-cli/tree/65006ce22099563526dcaca743451e99e9d834f7) [GitHub locations](https://github.com/github/docs/blob/be8d08aa6e3a95d7f531c6a00cbeff883e4e9814/content/copilot/concepts/agents/about-agent-skills.md) [VS Code locations](https://github.com/microsoft/vscode/blob/4e4877b113b1c34f3f01f08138038fe564e84171/src/vs/workbench/contrib/chat/common/promptSyntax/config/promptFileLocations.ts#L169-L180)
- Codex's public product page still renders `/etc/codex/skills` for the admin scope without a Windows row. `%ProgramData%\OpenAI\Codex\skills` is supported by current source composition, but is not stated on that product page. [Codex docs](https://developers.openai.com/codex/build-skills#where-codex-loads-local-skills) [Codex source](https://github.com/openai/codex/blob/21c58c90f2298587c6519e077d0692ce4c563d37/codex-rs/ext/skills/src/host_roots.rs#L77-L122)
- OpenCode's documentation requires unique names but does not define precedence; its current concurrent implementation should not be elevated into a stable precedence contract. [OpenCode docs](https://github.com/anomalyco/opencode/blob/13c27598d35f6f91fa4763a0b61a220ab7fcb263/packages/web/src/content/docs/skills.mdx#troubleshoot-loading) [OpenCode source](https://github.com/anomalyco/opencode/blob/13c27598d35f6f91fa4763a0b61a220ab7fcb263/packages/opencode/src/skill/index.ts#L235-L246)
- Local Windows global roots do not establish availability in vendor-hosted/cloud sessions. This report does not treat a local personal directory as a cloud distribution mechanism; each vendor's project, plugin, sync, or managed distribution paths are separate concerns.
